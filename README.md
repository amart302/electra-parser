# Парсер каталога

Одноразовый загрузчик на NestJS с Puppeteer и Prisma. PostgreSQL запускается в Docker, парсер — отдельным процессом Node.js на той же машине. HTTP-сервер и Swagger не используются.

Парсер обходит каталог и сохраняет товары в PostgreSQL. `Product` содержит основные данные, а размеры, электрика, внешний вид и упаковка хранятся в связанных моделях `ProductDimensions`, `ProductElectrical`, `ProductAppearance` и `ProductPackaging`. Записи групп создаются только при наличии значений; отдельные неприменимые поля внутри группы могут быть `NULL`.

Редкие, новые и неразобранные характеристики сохраняются через `Attribute` и `ProductAttribute`. Для составных значений вроде `8+5`, `60W+6W` и `10/20/30 W` сохраняется исходная строка вместе с вычисленным количеством или максимумом в группе. Известные характеристики имеют читаемые ключи. Каждая запись `ProductAttribute` содержит ровно одно значение: текстовое, числовое или логическое.

Сохранение товара, групп и характеристик выполняется одной транзакцией. Повторный обход заменяет характеристики источника, удаляет отсутствующие группы и сохраняет вручную указанную цену. Парсер выводит прогресс каждые 100 товаров и общий итог.

Перед запуском схема базы должна соответствовать `prisma/schema.prisma`: одного `prisma generate` недостаточно для создания таблиц. При переходе со старой структуры требуется перенос значений из колонок `products` в новые таблицы. Парсер не меняет схему БД и не переносит старые данные автоматически.

## Подготовка

Нужны Node.js 26.x, npm 11.x, Docker и Docker Compose.

```bash
cp .env.example .env
npm ci
```

Отредактируйте `.env`: задайте `TARGET_URL`, пользователя, пароль и название базы. Значения в `DATABASE_URL` должны соответствовать `DATABASE_USER`, `DATABASE_PASSWORD` и `DATABASE_NAME`. Адрес базы для парсера на той же машине — `localhost:5432`.

При установке зависимостей генерируется Prisma Client. Puppeteer также требует установленного браузера и системных библиотек: на Linux подготовьте их перед запуском парсера.

## PostgreSQL в Docker

Compose запускает только PostgreSQL 17:

```bash
docker compose up -d --wait postgres
docker compose ps
docker compose logs -f postgres
```

Порт доступен только на `127.0.0.1:5432`. Данные сохраняются в именованном томе `postgres_data`. Не меняйте имя Compose-проекта при повторном запуске: от него зависит имя тома.

Пользователь, пароль и база создаются при первой инициализации пустого тома. Изменение `.env` не меняет учётные данные существующей базы.

Остановить контейнер, сохранив данные:

```bash
docker compose stop postgres
```

Удалить контейнер и сеть, сохранив том с данными:

```bash
docker compose down
```

Не используйте `docker compose down -v`, если данные нужно сохранить: эта команда удаляет том базы.

## Миграции

Миграции выполняются через Node.js на машине с парсером. Compose не применяет их автоматически.

В проекте уже есть модели, но пока нет первой миграции. Создайте её на базе разработки и сохраните полученные файлы `prisma/migrations` в Git:

```bash
npm run prisma:migrate -- --name init_catalog
npm run prisma:generate
```

На сервере применяйте готовые миграции:

```bash
npm run prisma:migrate:deploy
```

Генерация Prisma Client сама по себе не создаёт таблицы.

## Запуск парсера

Для разработки:

```bash
npm run start:dev
```

Для одноразового запуска на сервере после подготовки браузера и применения миграций:

```bash
npm run build
npm run start:prod
```

При работе через SSH запускайте длительную загрузку внутри `tmux`, чтобы отключение терминала не остановило процесс. После завершения парсера PostgreSQL продолжает работать независимо от него.

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | Подключение Prisma к PostgreSQL |
| `DATABASE_USER` | Пользователь при создании базы в Docker |
| `DATABASE_PASSWORD` | Пароль пользователя при создании базы в Docker |
| `DATABASE_NAME` | Имя базы при создании в Docker |
| `TARGET_URL` | Начальная страница для обхода |

Файл `.env` не хранится в Git. Если пароль содержит специальные символы, кодируйте их в части пароля внутри `DATABASE_URL` как URL-компонент; в `DATABASE_PASSWORD` оставляйте исходное значение.

## Структура

```text
prisma/schema.prisma              # модели каталога
src/browser/browser.service.ts    # жизненный цикл Puppeteer
src/parser/catalog.service.ts     # извлечение данных сайта
src/parser/parser.service.ts      # управление обходом
src/prisma/                       # подключение к PostgreSQL
src/common/config/                # проверка окружения
src/app.module.ts                 # регистрация зависимостей
src/main.ts                       # одноразовый запуск и завершение
```

## Проверки

```bash
npm run lint
npm run typecheck
npm run build
```

Prisma Client генерируется в `src/generated/prisma` и не хранится в Git. Перед коммитом Husky запускает `lint-staged` для подготовленных TypeScript-файлов.

## Стиль кода

Для файлов и каталогов используйте `kebab-case`, для классов — `PascalCase`, для переменных и функций — `camelCase`. Форматирование определяет Prettier, а правила качества кода — ESLint; перед коммитом они применяются к подготовленным TypeScript-файлам автоматически.

### Импорты и alias

Alias `@/` указывает на каталог `src/` и настроен через `paths` в `tsconfig.json`.

- Для соседних файлов и связей внутри одного модуля используйте относительные пути: `./` или короткие `../`.
- Для обращений к другим модулям, общему коду и сгенерированному Prisma Client используйте `@/`.
- Импорты внешних пакетов и встроенных модулей Node.js оставляйте без alias. Сгенерированный код Prisma вручную не редактируйте.

```ts
// Соседний файл внутри src/prisma
import { PrismaService } from './prisma.service';

// Другие части проекта
import { PrismaService } from '@/prisma/prisma.service';
import { PrismaClient } from '@/generated/prisma/client';
```

При сборке через `npm run build` Nest CLI преобразует alias в относительные пути в JavaScript. Выбор между относительным путём и alias — соглашение проекта; ESLint проверяет сортировку импортов, но не обеспечивает соблюдение этого правила.

### Остальные соглашения

В Prisma называйте модели в `PascalCase`, а их поля — в `camelCase`. Названия таблиц в PostgreSQL задавайте в `snake_case` через `@@map`.

В IDE можно включить форматирование Prettier при сохранении. Комментарии добавляйте там, где они объясняют причину решения или неочевидное поведение; очевидный код не требует пересказа.
